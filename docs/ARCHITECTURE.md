# Как устроен Seruen

Seruen — пешеходный помощник по Астане на ближайшие 30–120 минут. Он отвечает 1–3 местами (или мини-маршрутом), и у каждого места указаны: почему оно подходит, сколько идти, сколько там пробыть, что делать и насколько можно верить часам работы.

## RAG-подход простыми словами

**Retrieval (поиск).** Система ищет по своей базе мест Астаны, собранной автоматически из открытых источников. Отбирает только места в пешей досягаемости, которые будут открыты к приходу и подходят под условия. Поиск идёт по словам (BM25) и по смыслу (векторы).

**Augmentation (дополнение).** Код добавляет контекст: время по Астане, закат, праздники РК, погоду. Потом считает оценку и строит маршрут.

**Generation (генерация).** ИИ получает факты о уже выбранных местах и пишет «почему» и «что делать» на языке пользователя.

**Ключевой принцип: код считает, ИИ объясняет.** Языковые модели плохо держат жёсткие ограничения: на бенчмарке TravelPlanner модель в одиночку выполнила все условия в 0,6 % задач, а связка «модель + решатель» — в 93,9 %. Поэтому расстояния, часы работы, погоду, порядок и время маршрута считает код. Модели разрешено только две вещи:
1. понять свободный текст (если правила не справились);
2. написать объяснения про ID, которые выбрал код.

## Путь одного запроса

1. **Браузер.** Точка превращается в клетку ~150 м; отправляются клетка, текст, фильтры и язык.
2. **Оркестратор.** Параллельно вызывает:
   - `nlu` — текст → условия: время, дети, коляска, интересы, «дальше аэропорт»;
   - `context` — время UTC+5, закат, праздник, погода → режим «гулять / коротко / в помещении»;
   - эмбеддинг запроса через `llm-gateway`.
3. **`retrieval`.** Радиус по бюджету времени и скорости (4,5 км/ч, с ребёнком 3,5 км/ч, коэффициент обхода 1,3, замерен на 105 парах в Астане) → жёсткие фильтры → гибридный поиск в OpenSearch (гео + BM25 + k-NN) → до 80 кандидатов.
4. **`ranking`.** `0,35·релевантность + 0,25·близость + 0,15·уверенность в часах + 0,15·погода + 0,10·популярность`, затем разнообразие: не три кофейни подряд.
5. **`routing`.** Минуты пешком по своему OSRM (граф дорог Астаны) → перебор маршрутов до 3 остановок с окнами работы, лимитом уличных отрезков в холод, временем визита и дорогой до аэропорта.
6. **`catalog-api`.** Свежие карточки из PostgreSQL → **поток `cards`**: факты появляются за 1–2 с.
7. **`explain`.** Вызов ИИ с JSON-схемой, где `poi_id` — перечень ID кандидатов. Затем **`guard`** проверяет ID, язык, отсутствие цифр и маркеров инъекций; всё, что не прошло, заменяется шаблоном → **поток `text`**.
8. **Поток `trace`.** Что использовано, что ушло в ИИ, что не уходило, время каждого шага.
9. **Kafka `reco.served`.** Обезличенное событие для аналитики города.

## Данные

| Источник | Что даёт | Лицензия |
|---|---|---|
| OpenStreetMap (Overpass, запасной вариант — выгрузка Geofabrik) | основа: координаты, категории, часы, доступность | ODbL, указываем авторство |
| Overture Maps Places | дополнительные заведения (confidence ≥ 0,6) | по источникам Overture |
| Wikidata | многоязычные названия, популярность (число статей) | CC0 |
| Wikivoyage | готовые описания «что посмотреть» | CC BY-SA |
| visitastana.kz | курированные подборки, коворкинги | ссылка на источник |
| sxodim.com | афиша событий (schema.org Event) | ссылка на источник |

**Живой слой 2GIS.** Сервис `places-live` в момент запроса ищет места вокруг клетки ~150 м через 2GIS Places API: свежие часы работы, рейтинг и отзывы, доступность для колясок. Совпадающие места (≤ 80–200 м и похожее название) склеиваются с нашей карточкой. Данные 2GIS ничем не сохраняются (п. 4.2 правил API), показываются с пометкой «2GIS» и обязательной подписью «Работает на API 2ГИС». Дневной лимит запросов защищает ключ; без 2GIS система работает на своей базе. Для продакшена нужен коммерческий договор с 2GIS.

2GIS, Google и Яндекс в собственной базе не хранятся: их условия это запрещают. Поэтому вместо рейтинга используется честный заменитель популярности: число языковых статей Википедии, число подтвердивших источников и наличие в подборках.

У каждого поля записаны источник, дата и уверенность (`источник × свежесть × согласие источников`). Сбор автоматизирован:
- CronJob по каждому источнику (раз в сутки, афиша — раз в 3 часа);
- Kafka `poi.raw` → normalizer → staging → dedup (имя + расстояние ≤ 250 м) → каталог → `poi.changed` → embedder → `poi.embedded` → indexer → OpenSearch.

## Развёртывание

Микросервисы работают внутри одного кластера DigitalOcean Kubernetes: 4 узла по 8 ГБ, Франкфурт.

| Слой | Что |
|---|---|
| Вход | Балансировщик DO → ingress-nginx → cert-manager (Let's Encrypt) |
| 14 онлайн-сервисов | orchestrator, session, context, nlu, retrieval, ranking, routing, explain, guard, llm-gateway, catalog-api, events-api, feedback-api, partner-portal |
| 9 фоновых воркеров | 6 сборщиков (CronJob), normalizer, dedup, quality, enrich, embedder, indexer, verifier (Celery), analytics |
| Шина | Kafka (Strimzi, KRaft, 1 брокер), 10 топиков |
| Хранилища | PostgreSQL + PostGIS (CloudNativePG), OpenSearch (k-NN), Redis, ClickHouse, MinIO, OSRM |
| Платформа | Linkerd (mTLS между сервисами), KEDA (масштаб воркеров по очереди), HPA, Argo CD, Prometheus + Grafana, Loki, Tempo (OpenTelemetry), Vault (dev) |

Один образ на все роли, роль задаёт `SERVICE`. В режиме `SERUEN_MODE=local` тот же код работает одним процессом (модульный монолит): так удобно разрабатывать и показывать демо без сети. Между сервисами ходят HTTP/JSON, gRPC — в планах.

## Ограничения

- Часы работы есть лишь у ~четверти мест в OSM, доступность — у ~4 %. Система это показывает, а не скрывает.
- Нет рейтингов внешних сервисов: их нельзя хранить.
- Kafka, базы и OpenSearch — по одной копии: это демо-кластер, не продакшен. Полная схема описана в плане развития.
- Качество казахского у модели не измерено независимыми бенчмарками; интерфейс переведён вручную.
